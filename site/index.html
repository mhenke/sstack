sad stack · negative testing for AI coding agents

Don't ask whether the software is robust.

sstack goes looking for the not-happy test cases, the ones nobody writes tests for on purpose. For each way your software fails, it writes a test that fails today and applies the minimal fix that turns it green.

Oracle first

The oracle is written before the attack. "It crashes" isn't an expectation. "It raises a validation error naming the field" is.

A test that passes against code you just proved broken has pinned the bug, and a pinned bug is worse than no test at all.

How it runs

Eight stages, every case executed for real.

  1. 1

    Discover

    Map surfaces and assumed contracts. Read learn/ first and prioritize adjacent surfaces of known failure classes.

  2. 2

    Attack

    Seven lenses, one attacker agent each, cases run in parallel. The command takes a scope: a file, a directory, a module, a package, or a URL.

  3. 3

    Verify

    Observed behavior against an oracle declared before the attack. One oracle, one observable outcome.

  4. 4

    Minimize

    Reduce to the smallest reproduction.

  5. 5

    Test

    Write the regression test and watch it go red on the bug.

  6. 6

    Fix

    Apply the minimal change that turns it green.

  7. 7

    Learn

    Record the failure class so the next run finds adjacent breakage.

  8. 8

    Report

    One finding per confirmed violation, evidence through the shipped emitter, machine-replayable.

Seven lenses, shipped

Each lens is one failure class.

boundaries

Edge cases: numbers, sizes, indexes, slices, collections, pagination, loops.

malformed

Strings parsed from outside, JSON, encodings, dynamic types.

missing

Optional fields, records from external data, null, None, undefined.

ownership

Subject, object, action, context. BOLA and IDOR, deny-by-default, privilege escalation, token tampering, CORS.

exceptional-conditions

Fail-open paths, diagnostic leakage, cascading failures, empty catch blocks.

resource-exhaustion

Connection pools, rate limits, memory ceilings, payload limits, disk.

state

Cached reads that never invalidate, mutable input written through, partial update after a failed call, internal collections escaped to callers.

your own

Drop a file with an sstack- prefix in your tree and the next run picks it up. No pack change needed. How it works

deferred

Ordering, concurrency, idempotency, dependency-failure, contract, mutation, and agent lenses are specified and unbuilt. Any of them can be activated by a user file.

Is it actually any good?

The eval is a cold agent.

No memory, no answer key, current skills and agents. The grader matches findings to the answer key by content, and replay re-audits each finding's evidence file with the agent out of the loop.

What it leaves behind

Run output in your repo, on your machine.

.sstack/
├── config.md     lenses.remove only, if you skip one (optional)
├── map.md        surfaces + assumed contracts
├── plan.md       lenses, cases, oracles
├── learn/        failure classes for the next run
├── findings/     one .md and one .json per finding
└── scratch/      throwaway attack scripts (gone at run end)

Plus regression tests and fixes. Tests land in your suite, fixes land in your source, and config and secrets stay read-only.

The four rules

The whole ethos, four lines.

1

Attack assumptions

Every input, state, and dependency an implementation assumes is a surface to probe.

2

Define the oracle before the attack

Write down the expected behavior under the adverse condition before running anything. One oracle, one observable outcome.

3

Never accept an agent's claim as evidence

Run the real command, quote the real output. The agent interprets evidence; it does not manufacture it.

4

Turn confirmed failures into a test and a fix

Write the regression test, apply the minimal fix, and add hardening tests for surfaces the system already handles.
